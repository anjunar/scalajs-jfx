## Executive Verdict

**RELEASE AFTER P0 FIXES.** Two confirmed release blockers: the documented TypeScript install fails because the required CSS 3.x package is absent from npm, and the Scala demo's advertised nested destination returns GitHub's generic 404 on direct access. Seven P1 findings concern the showcase's public contract, code/documentation accuracy, and presentation; one P2 concerns copying Scala examples.

An experienced developer can identify the broad value and understand the shared runtime from the README, but the five-minute path to trying it is not dependable. The most likely early exits are an unproven tagline with no immediate API sample, JFX2/JFX3/v1 contradictions, and the npm resolver failure. The runtime architecture inspected is compelling; it does not need a rewrite to address these findings.

**Coverage limitation:** This is a completed, time-boxed static/HTTP audit, not a complete interactive release sign-off. No VERIFIED-LIVE claims are made. Production build/tests, real hydration, console errors, JS-disabled interaction, mobile, and theme/history flows still require the checklist below before full approval.

## P0 — Release Blockers

### F0 — The documented npm quick start cannot resolve its dependencies

- **Evidence — VERIFIED-STATIC (registry metadata + executed resolver):** `README.md:58–60` instructs `npm install @anjunar/jfx-core @anjunar/scalajs-jfx-bridge @anjunar/scalajs-jfx`. Running that exact package list with `--dry-run --ignore-scripts --package-lock=false --no-audit --no-fund` in a fresh temporary directory using npm 11.17.0 exits 1 with `ERESOLVE unable to resolve dependency tree`. [Published core metadata](https://registry.npmjs.org/@anjunar%2fjfx-core/latest) is 3.0.0 and requires `@anjunar/scalajs-jfx: ^3.0.0`; [the complete stylesheet registry](https://registry.npmjs.org/@anjunar%2fscalajs-jfx) contains only 1.0.7, 1.0.8, 1.0.9, and 1.1.0 (latest). The checkout's `npm/scalajs-jfx/package.json:3` is already 3.0.0, so workspace resolution conceals the public mismatch. Resolver log: `C:/Users/Patrick/AppData/Local/Temp/jfx-release-audit-019c5a8e729b4deebea2a565296a6d3e/cache/_logs/2026-09-05T19_23_09_686Z-eresolve-report.txt`.
- **Impact:** The first documented TypeScript install fails before a developer reaches any example. This meets the release-blocker definition; it is not merely a stale version badge.
- **Root-cause evidence — VERIFIED-STATIC:** `scripts/publish-npm.ps1:15–26` explicitly excludes the standalone CSS package from its publication set even though core requires its 3.x release. The script's package-name guard also excludes that package. This makes the release-set omission concrete; it is not explained by an unpublished checkout alone.
- **Recommended direction:** Publish and verify the compatible CSS release as part of the same package release set, or explicitly gate the facade release on the required stylesheet already being public. Gate public instructions against an isolated registry consumer. Do not recommend peer-dependency bypass flags.

### F5 — The Scala router demonstration has an unshipped nested URL; generated error pages are not wired into Pages

- **Evidence — VERIFIED-STATIC (source + public HTTP):** `application/src/main/scala-3/app/pages/RouterPage.scala:59–61` exposes `Open /router/user/42` and navigates there. `AppRoutes.scala:77–86` declares the child. ## P1 — Important Before Promotion

### F1 — The landing page makes the central promise without showing either API

- **Evidence — VERIFIED-STATIC:** [Public landing page](https://anjunar.github.io/scalajs-jfx/) returns HTTP 200 with a tagline, five capability labels, two demo cards, and a repository footer link. Its complete HTML contains no code example. `tools/build-pages.mjs:170–232` generates that same page. The two demos also make the visitor choose a path before seeing an equivalent Scala/TypeScript example.
- **Impact:** In the first 10–60 seconds, visitors understand the category but cannot assess syntax, ergonomics, or the claimed equivalence. The strongest differentiator remains an assertion.
- **Recommended direction:** Put one small, equivalent, complete Scala/TypeScript example directly below the short value proposition, with links to runnable starters.

### F2 — The public journey contradicts itself about product identity and version

- **Evidence — VERIFIED-STATIC:** Landing: `JFX`; [Scala entry](https://anjunar.github.io/scalajs-jfx/scala/): `Welcome to JFX2`, sidebar `The JFX2 vision`, footer explaining inherited JFX2 design, toolbar `v1 demo`. [TypeScript entry](https://anjunar.github.io/scalajs-jfx/typescript/): `@anjunar/jfx` and a description referring to JFX3. `README.md:1` calls it JFX3; `build.sbt:30` sets `3.0.0`. Relevant sources: `application/src/main/scala-3/app/pages/OverviewPage.scala:18–29`, `app/App.scala:60,207,289–290`. The observed version indicator is a plain div, not release navigation. No v2.2.9 was observed.
- **Impact:** A visitor cannot confidently distinguish product generation, artifact version, and demo version. This directly weakens trust in the release and the shared-runtime story.
- **Recommended direction:** Choose one public product name; distinguish repository/package names explicitly; derive version presentation from release metadata and link it to release notes.

### F3 — The Scala demo delays concrete value with origin and vision copy

- **Evidence — VERIFIED-STATIC:** The root landing is concise and does **not** lead with philosophy. However, its Scala card opens a page whose content order is welcome → 17-year origin story → vision → capability metrics → i18n demonstration. `application/src/main/scala-3/app/pages/OverviewPage.scala:18–43` and public Scala HTML agree. The origin paragraph criticizes other frameworks without examples or supporting evidence.
- **Impact:** The first Scala-specific encounter spends attention on history and broad comparative claims before proving the API or explaining how to try it.
- **Recommended direction:** Lead the Scala overview with a small working example and explicit benefits; move personal history to an About section and replace comparative assertions with concrete behavior.

### F4 — The showcase lacks a complete first-run path and a clear release contract

- **Evidence — VERIFIED-STATIC:** The full root and demo entry HTML has no installation/Quick Start link. The TS shell (`npm/jfx-demo/src/app/shell.ts:35–79`) offers brand, Search, theme, locale, and package navigation but no repository, landing, Scala, or releases link. `README.md:31–78` offers paired counter bodies but neither a complete consuming project nor executable startup commands for those counters; Scala coordinates require another README. `jfx-core/README.md:11–15` does give the 3.0.0 dependency and sbt 2 caveat. MIT appears in README/package/POM metadata, but `git ls-files '*LICENSE*'` returns no file, and [GitHub license lookup](https://api.github.com/repos/anjunar/scalajs-jfx/license) returns 404. The latest-release endpoint also returns 404 (this does not prove no tags or prereleases exist). No explicit stability/support policy is stated in the entry pages or main/core READMEs inspected.
- **Impact:** Within five minutes, a visitor can learn what JFX is but must assemble installation, mounting, styling, demo startup, and release expectations from several files. The missing license document weakens a practical adoption decision even though MIT metadata is present.
- **Recommended direction:** Add a prominent shared Quick Start with complete minimal Scala and TS starters, supported tool versions, stylesheet imports, run commands, current release links, explicit maturity/support expectations, and a repository MIT license document. Keep source/landing/other-API links accessible from both demos.

### F7 — The Pages artifact drops public files used by the Scala shell

- **Evidence — VERIFIED-STATIC:** Public [GitHub toolbar image](https://anjunar.github.io/scalajs-jfx/scala/GitHub_Invertocat_Black.svg) and [favicon](https://anjunar.github.io/scalajs-jfx/scala/favicon.svg) return HTTP 404 with HTML content type, although the Scala entry references them. ### F8 — The public static demo promises request-dependent SSR fallbacks that its host cannot provide

- **Evidence — VERIFIED-STATIC (HTTP response comparison):** The public TS remote table says its footer works without JavaScript and renders the requested page on the server. Its own Next link targets `/typescript/en/controls/remote?remote-rows.offset=50&remote-rows.limit=50`. [That URL](https://anjunar.github.io/scalajs-jfx/typescript/en/controls/remote/?remote-rows.offset=50&remote-rows.limit=50) still serves `Page 1 of 100` and identical application HTML to the unparameterized URL. Scala `/en/table/?table.offset=10&table.limit=10` does the same. The Scala editor explicitly advertises a textarea for `?article.editor=editable`, but [its Edit destination](https://anjunar.github.io/scalajs-jfx/scala/en/editor/?article.editor=editable) still contains zero textarea elements and identical application HTML to read mode. TS `/router/params/42/?tab=activity` renders `queryParams: {}`. Comparison excluded script/style contents and TS code blocks to focus on served application markup. `server/prerender-pages.mjs:48–66` and `npm/jfx-demo/scripts/prerender-pages.mjs:36–55` generate path snapshots without query variants; the Node SSR entry points do accept request URLs, but GitHub Pages does not run them.
- **Impact:** Visitors following the documented fallback links receive first-page/read-mode HTML, undermining the non-JavaScript demonstration. A client adopting a different query state is a credible hydration risk, **INFERRED**, not a verified crash or DOM mismatch. Actual JS-disabled interaction and post-hydration controls are **NOT YET VERIFIED**.
- **Recommended direction:** Demonstrate request-dependent SSR on a server deployment, or make static showcase destinations correspond to actual pre-rendered states and scope the public claims to that deployment. Keep the general runtime's SSR capability distinct from what Pages can demonstrate. Verify both the raw response and real JS-disabled navigation after the change.

### F9 — Public Scala documentation displays obsolete, non-copyable API syntax

- **Evidence — VERIFIED-STATIC:** [The Scala layout page](https://anjunar.github.io/scalajs-jfx/scala/layout/) serves the literal text `style { gap = \"10px\" }` and `div { text = DemoI18n.text(i18n\"Left\") }`. In `application/src/main/scala-3/app/pages/LayoutPage.scala:106–116`, this is a triple-quoted Scala string, so those backslashes are displayed rather than escaping the quotation marks. `I18nPage.scala:53` also teaches `DemoI18n.text(...)`; no DemoI18n object/class/trait exists in the inspected application/core Scala sources. The current layout code itself uses `text(i18n"...") {}` and the current text builder is in `jfx-core/src/main/scala-3/jfx/core/layout/TextComponent.scala:36–45`. TS examples, by contrast, are extracted from their actual source with `?jfx-code` and displayed adjacent to the example body.
- **Additional evidence — VERIFIED-STATIC:** `README.md:54` and `jfx-core/README.md:48` describe a Scala `Runtime.hydrate` entry point, but `jfx-core/src/main/scala-3/jfx/core/component/Runtime.scala` exposes mount/render methods and no hydrate method. The real Scala `Main.boot` supplies a HydratingCursor to Runtime.mount and completes hydration after draining async work; TS does export a convenience `hydrate` function. The API relationship should be explained accurately rather than forcing identical method names into prose.
- **Impact:** Copying a prominent Scala layout example gives invalid syntax and an unavailable helper; the root README also sends Scala users toward a nonexistent convenience method. This is not a claim that every example or the root counter body is broken. It damages first-run confidence and the accuracy of the API symmetry story.
- **Recommended direction:** Replace the obsolete examples with current public API snippets that compile, and derive displayed Scala examples from checked source where practical. Preserve the TS source-derived approach. Document or inline demo-specific helpers in anything presented as a standalone starter.

## Showcase Strengths — Preserve These

- **One runtime, two APIs — VERIFIED-STATIC:** `npm/jfx-core/src/runtime.ts:43–70` delegates state, mount, hydrate, and SSR to the installed runtime. `jfx-bridge/src/main/scala-3/jfx/bridge/JfxRuntimeBridge.scala:22–26,33–35,43–114` wraps Scala properties and calls the same core Runtime and cursors. The adjacent `PropertyHandle.scala:16–46` forwards reads, writes, derived values, and observation to Scala state. This is a real implementation boundary, not merely a marketing diagram.
- **Feature facades preserve the runtime boundary — VERIFIED-STATIC:** `npm/jfx-controls/src/table.ts:61–88` constructs a registered table component; `ControlFactories.scala` maps its data source to Scala RemoteListProperty and its control factories instantiate Scala controls. `npm/jfx-forms/src/form.ts` adapts TypeScript models/validator metadata into the registered form contract. The differing Scala contextual DSL and TS option/callback syntax is idiomatic API adaptation, not evidence of a second framework.
- **Useful pre-hydration documents — VERIFIED-STATIC:** Public entry, state, forms, table/remote, editor, and nested-route pages contain actual application content, inputs, data rows, code, and navigation in the HTTP HTML. Both heads link a separately built stylesheet. Preserve this foundation; do not equate its presence with verified JS-disabled usability, and fix F8's request-state limitation.
- **Shared SSR/client composition — VERIFIED-STATIC:** TS entry-server.ts and entry-client.ts compose the same i18n provider → document → viewport → router/shell shape. Scala Main renders/hydrates AppDocument. The code explicitly waits for async work and completes the hydration cursor. Actual DOM adoption and warning-free hydration were not observed.
- **Source-derived TypeScript documentation — VERIFIED-STATIC:** The public state/forms/table pages show imports and actual example functions; `docs/example.ts`, `docs/code-block.ts`, and the `jfxCode` Vite plugin connect rendered examples to source snippets. This is a strong defense against the snippet drift found on Scala.
- **Substantial demonstrations already exist — VERIFIED-STATIC:** Scala forms output includes named model-bound controls; the editor response includes semantic Markdown; the TS remote table contains the initial 50 data rows and paging links; Scala has a concrete app-shell layout example. Those inspected surfaces provide better proof than additional philosophy. Virtualized scrolling, editor interaction, validation feedback, and subsequent remote loads remain untested in a browser.
- **Source-first i18n and module mapping — VERIFIED-STATIC:** Scala overview uses English i18n messages with an adjacent catalog, TS example sources use matching i18n/property concepts, and the root README maps Scala modules to their TS packages (explicitly leaving WebAuthn Scala-only). Preserve that honest mapping and the TS homepage's facade description.
